Insurance question answering over a Hebrew document corpus

Finding the right paragraph
and proving it

How the system is built, why each piece exists, and what it actually does on real questions.

The task

A customer asks a question in Hebrew

קניתי חבילת eSIM מהספק ולא קיבלתי את ההנחה, למה?

"I bought an eSIM package from the provider and didn't get the discount — why?"

What we must produce

  • An answer in Hebrew
  • Citations: which file, which page
  • Every claim backed by that text

Where the answer lives

One paragraph, on page 2, of one PDF — among 571 documents and 20,520 passages.

Why it is hard

Four properties of this corpus

Legal structure

Policies are numbered clause trees. The answer is often a sub-clause whose meaning depends on its parent.

Numbers live in tables

Premiums, deductibles, waiting periods. A table read as prose becomes unusable.

Near-identical products

The same product in Bronze / Silver / Gold editions, with different numbers and near-identical filenames.

Two scripts, two directions

Hebrew body text, Latin filenames and URLs, English annexes. Both spellings of a product name occur.

The bar

An answer is correct only if both halves hold

1. It covers the facts

Everything the reference answer contains is present.

2. Every claim is supported

Each sentence is backed by the text we cited. Nothing extra.

The failure that surprised us

A true, helpful sentence that the customer did not ask about — a phone number, a nearby limit — fails half two. We spend the last chapter on this.

The whole system

Two stores built once, one path per question

◆Two dashed stores are built once, offline. Everything below them runs on every question.

1.5 · Tables

Tables break the usual assumption

Search needs prose

A search model scores a question against text. A grid of numbers with no sentences matches almost nothing.

The answer needs the grid

Summarise the table and the exact premium is gone. Truncate it and the row the customer needs disappears.

These pull in opposite directions, so we stopped choosing.

1.5 · Tables

1.6 · A trap we found

The pages that look perfect and help least

Each domain has a "frequently asked questions" page. Here is what is actually inside one:

שאלות נפוצות - ביטוח דירה … דלג לתוכן ראשי … אם עליי לבטל את הפוליסה, לאן עליי לפנות? … מה קורה לפוליסה במקרה של אבדן לרכב, לדירה או לעסק? … איך מבטלים ביטוח?

Questions and navigation only

No answers anywhere on the page. The answers are behind links we never followed.

What we do

Keep them indexed, exclude them from search results by default. 11 such pages.

A question-shaped page scores extremely well against a question. Noise that looks on-topic is worse than obvious noise.

1.8 · The file map

The index knows passages. It does not know products.

Nothing in the search index says that a product page, three proposal forms and an earthquake annex are the same product. So we built a separate map: one row per file, 557 rows.

Built from

  • The index — which files exist, how big
  • Page text — a human title and summary
  • The URL list — where each page came from

Built with no model

Pattern rules and keyword matching only. It runs in seconds and is fully deterministic.

Both scripts on one row

Title from page text is Hebrew; aliases from the filename are Latin. Either spelling finds this product. No transliteration involved — both strings simply live here.

Only 3 passages

The page is nearly empty. The actual policy numbers are in the PDFs — hence the related list.

1.8 · The file map

How a 3-passage page acquires 12 documents

Take distinctive words from the product title, then attach any same-domain PDF whose filename contains one. "Distinctive" means 5+ characters and not a word like "insurance" that appears everywhere.

Words from אדירה ארד - ביטוח מבנה דירה + aliases
אדירה adira ארד arad ביטוח מבנה דירה
dropped: ארד — 3 characters · arad — 4 characters · ביטוח — too common · מבנה, דירה — 4 characters

The only surviving words are the family name. The word that distinguishes Bronze from Gold and Silver — ארד — is three characters long and was filtered out.

Where it bites

Questions whose answer differs by edition — a Gold deductible versus a Bronze one. All three become eligible and nothing downstream knows they compete.

Why it survives

The map only decides which files are eligible. Ranking still happens over passage text, and edition names appear in that text.

Chapter 1 · Summary

Decisions made before any question

Kept

  • Rebuild clause hierarchy from the text
  • Split along the clause tree
  • Two versions of every table
  • Ship generated descriptions in the repository
  • Exclude the question-only pages from search
  • A separate map of files and products

Rejected

  • Fixed-size windows
  • Trusting the parser's heading levels
  • Feeding raw table grids to the search model
  • Truncating long tables
  • Running character recognition on digital PDFs

2.2 · Domain filter

Guess the domain, but leave a way out

A small model guesses which insurance domains the question belongs to. We then fill the candidate list 80 from those domains, 20 from everywhere.

Filter strictly — rejected

Higher scores on questions it routed correctly. But a wrong guess meant the right document was never a candidate, and the system refused to answer at all.

80 + 20 — kept

Slightly noisier candidate list, and refusals from misrouting dropped to zero. Those 20 open slots are pure insurance.

Those 20 slots widen the net, but they are not a cure — chapter 3 has a real question where the domain guess was wrong and all 20 still came back off-target.

2.3 · Using the file map

If we recognise the product, search only its files

1
match
Score the question against file titles, aliases and paths. Keyword matching, no model.
2
check three floors
Score high enough? Do the matched files hold enough passages? Does anything survive combining with the domain filter?
3
all three pass
Search that product's files — the page and its related PDFs.
3
any floor fails
Change nothing. Normal search runs. A vague question such as "what does home insurance cover" never triggers narrowing.

Three independent guards that all mean the same thing: when unsure, do nothing.

2.4 · Ranking

A cheap ranker, then an expensive one

Vector similarity finds passages that are about the topic. It is bad at telling which one actually answers the question. For that we score each question–passage pair directly — accurate, but far too slow for 100 passages.

2.4 · Ranking

The cheap scorer gets a vote, not a veto

The accurate model does not receive the cheap model's top 40. It receives the union of two independent top-40 lists.

Cheap scorer's top 40

Question and passage read together.

Vector ranking's top 40

Similarity only — a parallel opinion.

Merged → the shortlist

Measured over 8 real questions: 45–66 passages, averaging 57. About 17 per question survive only because the vector ranking insisted.

The cheap scorer was caught burying passages the accurate one would have kept — one sat at vector rank ~30 and cheap-scorer rank ~70. It can demote; it cannot delete.

2.4 · Ranking, measured live

Vector similarity produced a 40-way tie

Real question, real index: "How long do I have to file a claim after the damage occurred?"

Vector similarity, 40 candidates

0.8868  —  0.8959

A spread of 0.009 across all 40. It knows they are all about insurance claims. It cannot tell which one answers the question.

Chapter 3

When the search is not enough

A small agent that can look around — with a strict budget.

3.1 · Structure

Two separate jobs, two separate calls

The searcher

  • Decides whether the evidence is sufficient
  • Can call tools to get more
  • Never writes the customer's answer
  • Sees the top 5 results plus a list of what else was found

The writer

  • Sees all gathered passages
  • Writes the Hebrew answer
  • Marks which passages it used
  • Calls no tools

One model doing both tended to either ramble or forget to cite. Separating the jobs fixed both.

3.2 · The toolbox

Six tools, two rounds

ToolWhat it doesCosts a round?
read moreShow the next 5 results we already haveFree
look aroundList the headings on nearby pages of the same documentYes
openPull the full text of a specific passage inYes
find the productLook a product up in the file mapYes
search againNew search with a rewritten queryYes
doneStop and hand over to the writer—

Reading further down the existing list is free — it costs no search and adds nothing new. Only touching the corpus costs a round.

3.3 · What that trace shows

The system found it, discarded it, then found it again

Two reasonable guards, one wrong outcome

"Only narrow when confident" and "respect the domain guess" are both sensible. Together they let a wrong domain guess veto a correct file-map match.

The agent paid for the router's mistake

Looking a product up by name ignores the domain entirely — so it recovered what routing had excluded. Without the agent, this question fails.

The asymmetry is one branch: inside the search tool, file-map files that fall outside the guessed domain are preferred anyway. At seed time they are silently dropped. Making the two agree is the cheapest open improvement in the system.

3.4 · A real question, blocked

When the system refuses its own answer

מה מספר הטלפון של המוקד לתביעות ביטוח?

"What is the phone number of the insurance claims centre?"

1
searcher: done
"The number appears consistently across all sources — 03-9294000."
2
blocked automatically
"Deferred: the retrieved document titles cover only 20% of the question's content words (missing: number, phone, centre, claims). Run a file-map lookup with a short literal query first."
3
find the product
Looks up "claims centre phone" in the file map.
4
done → writer
Same number, now with a document that actually contains it. Answer cites a page carrying the number.

The rule is generic: if the titles of what we found barely overlap the words of the question, look it up by name before answering.

3.6 · Citations

The writer cites by number, not by name

Rejected

Letting the model write filenames and page numbers into its answer. It invents plausible ones.

Kept

Passages are numbered in the prompt. The model lists the numbers it used. We resolve those to file and page ourselves.

A citation can now be wrong about relevance, but it can never point at a document that was not in front of the model.

Chapter 4

Checking the answer

The failure mode that is hardest to see: being too helpful.

4.1 · The problem

A correct answer that fails

Question: is insurance required for an approved clinical trial?

Correct and supported → Yes, a clinical trials policy is required for every approved trial, covering participant injury claims and legal defence costs.

Then it added → להצטרפות ניתן להתקשר ל-2735*.  ("To join, call *2735.")

Nobody asked how to join. The sentence is helpful, plausible, and not supported by the cited text for this question — so the whole answer fails the support half of the bar.

4.2 · The checker

Delete, never rewrite

1
split
Break the answer into individual claims.
2
test each
Does this claim answer what was asked, and is it supported by the cited text?
3
delete the rest
Remove the unsupported ones. Never regenerate — a rewrite invents new claims, which is the problem we are solving.

Skipped when pointless

Refusals and very short single-claim answers skip the check entirely.

Measured

Ran on 101 of 109 questions · changed the answer in 8. Roughly two seconds when it runs.

4.3 · Results

4.4 · Honest limits

What still goes wrong

Near-identical editions

Bronze, Silver and Gold all eligible; nothing knows they compete. The three-of-twelve problem from chapter one.

Scanned forms

Some documents carry no extractable text. We drop that garbage rather than cite it, so those questions simply fail.

One fact off-page

Most remaining failures are a single date or amount that is real but not on the page we cited — not invented answers.

Close

Four things that generalise

No single cheap stage may delete evidence

The domain filter keeps 20 slots open, the cheap scorer's shortlist is merged with the vector ranking's, product narrowing does nothing unless confident.

Store data twice if uses conflict

Tables are described for finding and kept whole for answering.

Cheap first, expensive last

Every stage is more accurate and sees less than the one before it.

Deleting beats rewriting

Removing an unsupported sentence cannot introduce a new one.

In one sentence

Prepare the text carefully, search in narrowing stages, let a small agent repair the search when it misses, and delete anything the citations do not support.
